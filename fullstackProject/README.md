# CineBooking — фулстек-демо: бронирование билетов в кино

[![cinebooking CI](https://github.com/Dimas1Barabas/Dimas1Barabas.github.io/actions/workflows/cinebooking.yml/badge.svg)](https://github.com/Dimas1Barabas/Dimas1Barabas.github.io/actions/workflows/cinebooking.yml)

Монорепозиторий с полным циклом асинхронной обработки брони:

```
┌──────────┐  REST   ┌────────────┐        ┌──────────────┐
│ Vue 3 SPA│ ──────▶ │ NestJS API │ ◀─────▶ │ PostgreSQL   │
│ (Vite)   │ ◀────── │ (TypeORM)  │        └──────────────┘
└──────────┘         │      │     │        ┌──────────────┐
                     │      ├─────┼─────▶  │ Redis (кэш)  │
                     │      │     │        └──────────────┘
              publish│      │consume
              booking.created │ booking.processed
                     ▼      ▲
              ┌─────────────────┐
              │ RabbitMQ        │   topic-обмен «cinema»
              └────────┬────────┘
                       │ consume
                       ▼
              ┌─────────────────┐   booking.processed/.refunded/.expired
              │ Go ticket-worker│  «платёжный шлюз» + /stats
              └────────┬────────┘
                       │ вердикты
                       ▼
              ┌─────────────────────┐
              │ Go notification     │  «email-уведомления» + /notifications
              │ (гексагон)          │
              └─────────────────────┘
```

## Быстрый старт (всё в docker)

```bash
docker compose up --build
```

| Сервис | Адрес | Примечание |
|---|---|---|
| web (SPA) | http://localhost:18080 | nginx, /api → api |
| api (NestJS) | http://localhost:13000/api/health | health-check трёх зависимостей |
| Swagger UI | http://localhost:13000/api/docs | живая документация API (также через :18080/api/docs) |
| RabbitMQ UI | http://localhost:15672 | guest / guest |
| worker (Go) | http://localhost:8081/stats | счётчики оплат и возвратов |
| notification (Go) | http://localhost:18082/notifications | история «email»-уведомлений, гексагон |
| PostgreSQL | localhost:15432 | cine / cine, БД cine + cine_notifications |
| Redis | localhost:6379 | кэш фильмов, TTL 60 c |

Host-порты 13000/15432/18080 выбраны, чтобы не конфликтовать
с типичными локальными сервисами (3000/5432/8080).

При первом старте API применяет SQL-миграции (TypeORM, `apps/api/src/migrations`)
и сеет 6 фильмов с расписанием сеансов в Postgres (если таблица пуста).

## Разработка без docker (только инфраструктура в docker)

```bash
docker compose up -d postgres redis rabbitmq

# API (порт задаётся через PORT, если 3000 занят)
cd apps/api
npm install
PORT=13000 npm run start:dev   # http://localhost:13000/api
# схема применяется миграциями автоматически при старте

# Web (в отдельном терминале)
cd apps/web
npm install
npm run dev              # http://localhost:5173 (прокси /api → :13000)

# Go-воркер (платёжный шлюз)
cd services/ticket-worker
go run ./cmd/ticket-worker       # слушает RabbitMQ, /stats на :8081

# Go-уведомления (гексагональный сервис)
cd services/notification-service
go run ./cmd/notification        # слушает вердикты, HTTP на :8080
# персистентная история вместо кольцевой памяти:
STORAGE=postgres go run ./cmd/notification
```

### Миграции

Схему БД создают и меняют только миграции (`synchronize` убран) —
журнал в таблице `migrations`. Приложение применяет их автоматически
при старте (`migrationsRun: true`), руками — из `apps/api`:

```bash
npm run migration:show      # что применено / в ожидании
npm run migration:run       # применить ожидающие
npm run migration:revert    # откатить последнюю

# новая миграция: diff «сущности ↔ БД». Генерить нужно против ПУСТОЙ БД,
# иначе diff с уже собранной synchronize-схемой будет пуст:
docker compose exec postgres createdb -U cine cine_empty
DATABASE_URL=postgres://cine:cine@localhost:15432/cine_empty \
  npm run migration:generate -- src/migrations/AddSomething
docker compose exec postgres dropdb -U cine cine_empty
```

Файлы миграций лежат в `apps/api/src/migrations` и попадают в docker-образ
вместе с `dist` без правок Dockerfile.

`InitialSchema` написан руками через Table API (`queryRunner.createTable`) —
это тот же код-путь, что у synchronize, поэтому чистый том разворачивается
схемой, идентичной прежней synchronize-схеме. UUID-ключи используют
`gen_random_uuid()` (встроен в PG13+, extension не нужен). Имена индексов
и FK считаются `DefaultNamingStrategy` — так же, как делал synchronize,
чтобы будущие `migration:generate` давали чистый diff.

`AddSessions` — вторая миграция: у фильмов появляется расписание
(таблица `sessions`: фильм, зал, время), бронь и занятость мест
перепривязываются с фильма на сеанс (`uq (session_id, seat)`). Перенос
данных честный: единственный `session_at` фильма становится его сеансом,
существующие брони получают `session_id` обратным lookup'ом. На стенде
со старыми данными достаточно `docker compose up --build -d` —
миграция применится при старте.

## Как устроено

### Поток бронирования

1. `GET /api/movies` — SPA получает фильмы с расписанием: у каждого
   `sessions[]` (зал + время), отсортированные по времени, сама афиша —
   по ближайшему сеансу. Ответ помечен источником: при попадании в
   Redis-кэш (`movies:all:v3`, TTL 60 c) список не ходит в Postgres —
   во фронтенде это видно по бейджу «из кэша».
2. `GET /api/sessions/:id/seats` — карта занятости зала сеанса 8×10
   (без кэша, всегда свежая) для сетки мест в модалке брони.
3. `POST /api/bookings {sessionId, customerName, seats: ["5-7", "5-8"]}` —
   в одной транзакции сохраняется бронь `PENDING_PAYMENT` с дедлайном
   оплаты `expires_at` и занимаются места (фильм выводится из сеанса).
   Арбитр в гонке за место — составной уникальный констрейнт
   `(session_id, seat)` таблицы `seat_occupancy`: одно и то же место
   в разных сеансах одного фильма — независимые строки; проигравший
   в гонке получает 409 со списком занятых мест (`seatsTaken`).
4. Таймер резерва: API публикует событие в wait-очередь `booking.payment.wait`
   — она без потребителей, держит сообщение ровно окно оплаты
   (`PAYMENT_TIMEOUT_MS`, дефолт 15 мин; на стенде — 2 мин) и по TTL
   отдаёт его dead-letter'ом в `booking.payment.timeout` → Go-воркеру.
5. `POST /api/bookings/:id/pay` — оплата: условный `UPDATE` переводит
   `PENDING_PAYMENT → PENDING` (гонку с таймаутом и двойным кликом
   разрешает БД, проигравший получает 409) и публикует `booking.created`
   в topic-обмен `cinema` (RabbitMQ).
6. Go-воркер `ticket-worker` консьюмит `worker.booking.created`
   (prefetch = 1), имитирует оплату 1,2–2,8 с с вероятностью успеха ~90%,
   публикует `booking.processed` с вердиктом, местами и своим именем.
7. NestJS слушает `api.booking.processed` и обновляет бронь в Postgres:
   `CONFIRMED`/`FAILED` + сообщение от воркера (вердикт применяется только
   к `PENDING` — ределивери и «хвосты» старой топологии пропускаются).
   При `FAILED` занятые места освобождаются — их снова можно купить.
8. Просроченный резерв: по TTL wait-очереди воркер получает
   `booking.payment.timeout` и публикует `booking.expired`; API условным
   `UPDATE` из `PENDING_PAYMENT` гасит бронь в `EXPIRED` и освобождает
   места. Если клиент успел заплатить/отменить — `affected = 0`,
   событие молча пропускается (идемпотентность гонки pay-vs-timeout).
9. Неоплаченную бронь можно отменить напрямую: `PENDING_PAYMENT →
   CANCELLED` одним `UPDATE`, места свободны сразу, воркер не участвует.
10. SPA получает изменения мгновенно по Server-Sent Events:
   `GET /api/bookings/stream` (EventSource). Каждая мутация брони —
   create/pay/cancel/processed/refunded/expired — эмитит событие
   `booking` с самой бронью и свежей статистикой; каждые 25 c идёт
   heartbeat `ping`. При обрыве браузер переподключается сам, а по
   `onopen` фронт делает полный resync через `GET /bookings`. Опроса нет.
11. Каждый вердикт (`booking.processed`/`.refunded`/`.expired`) дублируется
   в Go-сервис `notification`: он превращает событие в клиентское
   «email»-уведомление (в стенде печатается в лог), хранит историю
   в собственной БД `cine_notifications` того же кластера (переживает
   рестарт; базу и схему сервис создаёт сам) и отдаёт её через
   `GET /notifications`. Построен гексагонально: домен и use-case
   в центре, брокер/HTTP/память/Postgres — заменяемые адаптеры за
   портами (`STORAGE=memory|postgres` переключает их строкой в main).

```
PENDING_PAYMENT ──pay──▶ PENDING ──воркер──▶ CONFIRMED | FAILED
      │                    ▲
      │        TTL wait-очереди (RabbitMQ, без cron)
      ▼                    │
   EXPIRED (места свободны) └─ просроченный таймер по оплаченной — пропуск
      │
      └──cancel──▶ CANCELLED (места свободны сразу, без воркера)
```

### Сага отмены (компенсация)

Подтверждённую бронь можно отменить — это отдельная асинхронная сага
с тем же воркером:

```
CONFIRMED ── POST /api/bookings/:id/cancel ──▶ CANCELLING
                          │ booking.cancelled (cinema)
                          ▼
                Go-воркер: «возврат платежа» 0,8–1,6 с (~90% успеха)
                          │ booking.refunded
          успех ◀─────────┴─────────▶ отказ (REFUND_FAILED)
            ▼                               ▼
CANCELLED + места свободны      бронь откатывается в CONFIRMED
```

- Переход `CONFIRMED → CANCELLING` — условный `UPDATE … WHERE status =
  'CONFIRMED'`: двойной клик по «Отменить» разрешается на стороне БД,
  проигравший получает 409 с текущим статусом.
- Места освобождаются **только после вердикта воркера** — если «банк»
  откажет в возврате, места остаются за клиентом, а бронь возвращается
  в `CONFIRMED` с сообщением об ошибке.
- Consumer `booking.refunded` идемпотентен: повторное событие (ределивери)
  по брони вне статуса `CANCELLING` пропускается.

### Надёжность доставки: retry-очереди и parking lot

Сбой обработки больше не теряет событие. У каждой рабочей очереди — и у
API (`api.booking.*`), и у Go-воркера (`worker.booking.*`) — есть пара
очередей надёжности:

```
                    сбой обработки (транзиентный)
  рабочая очередь ───────────────────────────────▶ `<очередь>.retry`
       ▲  новая попытка                                │ x-message-ttl 5 c
       └──────────────── dead-letter ◀─────────────────┘
       poison (JSON не разбирается / брони нет) или попытка 3 из 3
       └──────────────────────────────▶ `<очередь>.parking` — разбор руками
```

- Паузу между попытками делает брокер: retry-очередь живёт без
  потребителей, держит копию сообщения `x-message-ttl` 5 с и по
  dead-letter возвращает его в рабочую очередь. Код лишь публикует копию
  и ack'ает исходное.
- Счётчик попыток — заголовок `x-retry-count`, последняя ошибка —
  `x-last-error`: оба видны в RabbitMQ UI и в логах.
- «Ядовитые» сообщения ретраить бессмысленно, они едут в parking сразу:
  неразбираемый JSON в воркере, `NotFound` (брони уже нет) в API.
  Остальное (БД недоступна, публикация упала) переживает до 3 попыток.
- Механика симметрична на обеих сторонах: API — `errorHandler`
  у `@RabbitSubscribe` (`apps/api/src/rabbit/retry.ts`), воркер —
  `retryOrFail` (`services/ticket-worker/main.go`). Топологию (`*.retry`,
  `*.parking` + бинды) объявляют обе стороны одинаковыми параметрами.

### Авторизация (JWT + роли) и аккаунт

Витрина открыта всем, мутации — за Bearer-JWT:

- `POST /api/auth/register` — email + пароль (bcrypt на сервере) + имя;
  повторный email → 409 `emailTaken`.
- `POST /api/auth/login` — `{accessToken, user}`; токен живёт 2 ч,
  несёт `sub/email/name/role`, секрет — `JWT_SECRET`. Вместе с ним
  API ставит **httpOnly-cookie `cine.refresh`** (30 дней, Path=/api/auth) —
  refresh-сессия, которую JS не видит.
- Гварды по умолчанию закрывают всё (`deny by default`): `JwtAuthGuard`
  через `APP_GUARD`, открытые эндпоинты помечены `@Public()`
  (каталог, карта зала, статистика, SSE, health).
- `RolesGuard` следом сверяет роль с `@Roles(...)`: `POST /api/movies`
  (новый сеанс в афишу + сброс кэша каталога) — только админ.
- Бронь пишется на `user_id` из токена: имя покупателя берётся из профиля
  (поле `customerName` опционально), отменить чужую бронь нельзя (403).
- Личный кабинет: `GET /api/bookings/my` — только брони владельца из токена,
  свежие сверху; фильтрация — на стороне БД (`where user_id`), не на клиенте.
- При старте API сеется админ (`ADMIN_EMAIL`/`ADMIN_PASSWORD`, по умолчанию
  `admin@cine.local / admin-secret-1` — данные демонстрационные).
- SSE-стрим публичен осознанно: `EventSource` не умеет заголовок
  `Authorization`, а стрим — витринное демо-табло.
- На фронте: `/login` (вход и регистрация), токен в localStorage,
  `Authorization: Bearer` на всех запросах; вошедшему — `/my` «Мои билеты»
  (свои брони, кнопки «Оплатить»/«Вернуть билеты», мгновенные обновления
  по тому же SSE-стриму), админу — `/admin`, форма нового фильма
  с расписанием сеансов, и `/admin/stats` — дашборд аналитики.
  В демо-режиме на Pages авторизации нет — симуляция остаётся без токенов
  (аналитика в демо открыта всем).
- Экран оплаты `/pay/:bookingId` — после создания брони фронт ведёт туда
  автоматически: таймер окна оплаты, кнопка «Оплатить N ₽», состояния
  вердикта/истечения; статусы фронт не выдумывает — только SSE.

### Аккаунт: сессии, профиль, восстановление пароля

Сессия переживает протухание 2-часового access, аккаунтом можно управлять:

- **Refresh-ротация** (`TokensService`, таблица `refresh_tokens`): в БД —
  только sha256-хэш токена; `POST /api/auth/refresh` (@Public) читает
  httpOnly-cookie, гасит старый токен условным `UPDATE … WHERE revoked_at
  IS NULL` и выдаёт свежую пару + новую куку. Переиспользование отозванного
  токена — улика компрометации: ревокаются **все** сессии пользователя
  (гонку параллельных refresh решает тот же условный UPDATE).
- **Фронт самоисцеляется**: `client.ts` перехватывает 401 → один
  single-flight `POST /auth/refresh` на пачку запросов → повтор исходного
  (auth-роуты не перехватываются — их 401 приговор). Мёртвый refresh
  чистит локальную сессию.
- **Профиль** `PATCH /api/users/me` (имя/email, 409 `emailTaken`) и
  **смена пароля** `PUT /api/users/me/password` (неверный текущий — 403):
  ответы несут свежую пару — в JWT живут email/name, старый токен
  протух бы со старыми клеймами. Смена пароля ревокает все сессии,
  кроме устройства, где меняли.
- **Восстановление**: `POST /api/auth/forgot-password` всегда 200 (не
  оракул); для существующего email создаётся одноразовая ссылка
  (таблица `password_resets`: sha256-хэш, TTL 30 минут, одноразовость —
  условным UPDATE по `used_at IS NULL`) и публикуется событие
  `user.password.reset` → notification-service печатает «письмо»
  (на стенде видно в `:18082/notifications`, адресат — email).
  `POST /api/auth/reset-password` меняет пароль, ревокает сессии и сразу
  логинит устройство со ссылкой. Ссылка на фронт — env `RESET_LINK_BASE`.
- Страницы: `/profile` (две формы, чип юзера в шапке), `/forgot-password`,
  `/reset-password?token=…` («Забыли пароль?» на /login). В демо на Pages
  аккаунт зеркалируется движком: сессия в памяти до перезагрузки (любой
  email, `admin@cine.local` занят — честный 409), смена пароля и сброс —
  те же 403/400, а «письмо» печатается на экране ссылкой.

### Отзывы и рейтинги

Оценить фильм может только тот, кто ходил на него по нашей брони:

- `POST /api/movies/:id/reviews {rating: 1–5, text: 10–1000 символов}` —
  только за JWT и только при наличии **текущей** `CONFIRMED`-брони на
  этот фильм (вернул билеты — права нет; уже написанный отзыв остаётся).
- Один отзыв на пару (пользователь, фильм): арбитр — составной unique
  `uq_reviews_user_movie`, гонку дубля решает БД → 409 `reviewExists`
  (проигравший получает код в теле ответа).
- `GET /api/movies/:id/reviews` — публичный список, свежие сверху.
- `DELETE /api/movies/:id/reviews/:id` — свой отзыв или админ; поиск
  отзыва скоуплен по фильму — id чужого фильма до отзыва не доберётся.
- Средний балл и число отзывов денормализованы на фильме
  (`rating_avg`/`rating_count`) и пересчитываются **от источника** (не
  инкрементом) той же транзакцией, что и запись отзыва. После мутации
  сбрасываются оба кэш-ключа каталога (`movies:all:v3`, `movie:v3:{id}`) —
  рейтинг на карточках не ждёт TTL.
- На фронте: звёзды со средней и счётчиком прямо на карточке фильма
  (клик — модалка отзывов: список, удаление своего/админское, форма со
  звёздным вводом за `v-if` eligibility). Демо-режим зеркалит контракт:
  сид-отзывы «других зрителей», право гостя — своя CONFIRMED-бронь,
  те же 403/409 с теми же телами.

### Промокоды и скидки

Скидка применяется **в момент оплаты** — истёкшая или отменённая бронь
не сжигает активацию, а гонка за последний код решается ровно в точке
невозврата:

- `POST /api/promos {code, kind: percent|fixed, value, maxActivations,
  expiresAt}` — только админ; дубль кода ловит `uq_promos_code` →
  409 `promoExists`. Граница процента (≤ 99) проверяется сервисом —
  она зависит от `kind`.
- `GET /api/promos` — список для админки со счётчиком активаций.
- `POST /api/promos/validate {code, bookingId}` — превью **без списания**:
  скидка и итог по текущей сумме своей брони в `PENDING_PAYMENT`
  (403 чужая, 409 не ждёт оплаты). Ошибки — кодами: 404 `promoNotFound`,
  410 `promoExpired`, 409 `promoExhausted`.
- `POST /api/bookings/:id/pay {promoCode?}` — оплата с кодом одной
  транзакцией: условный UPDATE `PENDING_PAYMENT → PENDING` плюс
  атомарный инкремент
  `UPDATE promos SET used_count = used_count + 1 WHERE code = $1 AND
  used_count < max_activations AND expires_at > now() RETURNING …`.
  Проигравшему в гонке транзакция **откатывается целиком** — бронь
  остаётся payable, а причина (не найден/истёк/исчерпан) — общий
  `promoRefusalError()` для превью и оплаты.
- На брони запоминаются `promo_code` и `discount_rub`, `total_rub`
  становится итоговой суммой: воркер списывает её, сага возврата
  возвращает, аналитика считает — контракты не менялись.
- Экран `/pay/:id`: поле «Применить» (Enter), применённый код —
  зачёркнутая база, скидка и новый итог в кнопке; если код исчерпали
  между превью и оплатой — промо снимается с подсказкой, бронь
  остаётся оплачиваемой. Демо-паритет: сиды `CINE10` (−10%),
  `SUMMER300` (фикс, 2 из 3 — честный 409) и `EXPIRED5` (истёкший,
  410); секция промокодов в `/admin` открыта демо-режиму всем.

### QR-билеты на места

Билет — **производная брони, а не отдельная сущность**: нет таблицы,
миграции и синхронизации. Билеты существуют ровно тогда, когда бронь
`CONFIRMED`; сага возврата закрывает бронь — билеты гаснут сами,
откат `REFUND_FAILED` возвращает их без нашего участия. Подпись
детерминирована (`бронь + место + сеанс` + секрет), поэтому выдача
пересчитывается на каждый запрос и переживает рестарты API:

- `GET /api/bookings/:id/tickets` — по билету на каждое место, только
  владельцу (403 чужому); всё, что не `CONFIRMED` — 409
  `bookingNotConfirmed`. Каждый билет несёт `signature` (HMAC-SHA256,
  первые 128 бит hex — компромисс стойкости и плотности QR), номер
  `ticketNo` (`TK-XXXXXX`, детерминирован) и контекст фильма/сеанса.
- QR-строка `CINE1|bookingId|seat|epoch|signature` собирается на фронте
  из полей билета (`shared/lib/ticket.ts` — зеркало `ticket.logic.ts`
  API, как промокодная пара `promo.logic`/`promo.ts`; подпись считает
  синхронный `shared/lib/sha256.ts` — своя реализация, потому что
  `crypto.subtle` асинхронна; спек сверяет её с node:crypto).
- `POST /api/bookings/tickets/verify {payload}` — сканер на входе в зал,
  только админ. Отказ — не 4xx, а вердикт с причиной: `malformedPayload`,
  `badSignature` (сравнение `timingSafeEqual` — сканер наружный вход),
  `bookingNotFound`, `bookingNotConfirmed`, `seatMismatch` (чужое место
  при честной подписи), `sessionPassed` (сеанс уже прошёл).
- Секрет — `TICKETS_SECRET` по образцу `JWT_SECRET` (env + dev-дефолт,
  проброс в compose); смена секта гасит все ранее выданные билеты.
  В демо-режиме движок подписывает отдельным `demo-cine-tickets-secret`
  — демо-билеты не пройдут у живого сканера.
- Экран `/ticket/:bookingId`: карточка на место — градиентный хедер
  фильма, TK-номер, белый QR (контраст важнее темы интерфейса), ряд/место.
  Клик по QR — полноэкранный режим «у входа в зал» (Esc закрывает).
  Точки входа: CONFIRMED-ветка оплаты, строки «Моих билет» и демо-табло.
  QR рисует `qrcode-generator` (единственная новая зависимость) в чистый
  SVG: тёмные модули слиты в пробеги одним path, `crispEdges`.

### Лист ожидания (waitlist)

Аншлаг не теряет спрос: на полный сеанс можно встать в очередь и получить
уведомление, когда место освободится. Дизайн — **честная гонка**: уведомление
не резервирует место, кто первый успеет забронировать — тот и купил.

- `POST /api/waitlist/:sessionId` — вход в очередь. Только полный будущий
  сеанс: при свободных местах — 409 `sessionNotFull`, начавшийся —
  410 `sessionPassed`, повторный вход — 409 `waitlistAlready`. Ответ —
  честная позиция: порядковый номер среди WAITING. `DELETE` — выход:
  запись гасится в LEFT, повторный вход — в конец очереди.
- `GET /api/waitlist/my` — свои записи с контекстом фильма и позицией;
  LEFT и уже начавшиеся сеансы скрыты (лениво, без cron).
- Таблица `waitlist_entries` (миграция `AddWaitlist`): статус
  `WAITING/NOTIFIED/LEFT`, дубль решает `uq (session_id, user_id)`,
  `queued_at` обновляется при повторном входе — «выход-вход» не удерживает
  место в голове очереди.
- Освобождение места — событие в брокере, а не вызов. Все 4 точки, где
  места возвращаются в продажу (отмена неоплаченной, EXPIRED по TTL,
  FAILED-вердикт воркера, возврат по саге), публикуют
  `waitlist.seat.released` → очередь `api.waitlist.released` (с retry/
  parking). Консьюмер — сам API: голова WAITING переводится в NOTIFIED
  условным `UPDATE` (affected = 0 — ределивери, пропускается молча;
  ределивери после краша уведомит следующего — это безопасно, уведомление
  не резерв).
- Два канала уведомления: «письмо» `user.waitlist.seat` — пятый поток
  notification-service (адресат — email, в ссылке — `?movie=<id>`) —
  и витринное SSE-событие `waitlist` с userId: стрим публичен, «моё»
  фильтрует клиент.
- Успел в гонке — `POST /bookings` гасит его запись в LEFT тем же запросом
  (репозиторий напрямую из `bookings.service`): следующее освобождение
  достанется следующему в очереди.
- На фронте: модалка полного зала показывает CTA очереди с позицией вместо
  сетки мест, `/my` — блок ожидания и баннер «место освободилось» после
  NOTIFIED, из «письма» ведёт глубокая ссылка `?movie=<id>`. В демо на
  Pages очередь живёт в движке: сид-«аншлаг» сеанса «КиноКлуб» и те же
  переходы WAITING → NOTIFIED без сети.

### Live-карта мест (WebSocket)

Карта занятости в модалке брони — живая: чужая покупка серееет мгновенно,
освободившееся место возвращается в продажу, без перезагрузки и опроса
(до сих пор это ловилось 409-конфликтом при сабмите). Транспорт — чистый
WebSocket: `@nestjs/platform-ws` на бэкенде, нативный `WebSocket` на фронте,
ноль новых зависимостей фронта.

- Гейтвей `/api/seats` (`seat-map.gateway.ts`): комнаты по сеансу —
  `Map<sessionId, Set<client>>`; подписка кадром `{"type":"subscribe",
  "sessionId"}`, повторная подписка переключает комнату. Путь задан
  целиком в декораторе: глобальный префикс `api` — про HTTP-роутер,
  на гейтвеи он не действует; адаптер матчит upgrade по точному pathname,
  чужие пути закрываются `socket.destroy()`.
- Протокол симметричный JSON, маршрутизация кадров ручная
  (`client.on('message')`), не `@SubscribeMessage`: стандартный WsAdapter
  ждёт конверт `{event, data}` и молча глотает неразобранное — а здесь
  мусор честно получает `{type:"error"}` с причиной.
- **Снапшоты, не дельты**: на подписку и на каждое изменение — полный кадр
  `{type:"snapshot", data: SeatMap}` перезапросом `seatMap()` из БД. Payload
  ≤ 80 кодов мест, дрейфа и sequencing нет, единственный источник истины —
  `seat_occupancy`; пустая комната не ходит в БД вовсе.
- Сигнал — шина `SeatStream`: in-process rxjs-Subject, отдельная от
  `BookingStream` (у того другой контракт — DTO брони для табло). Хелпер
  `publishSeatsReleased` закрывает все 4 точки освобождения одной строкой,
  `create()` эмитит **после** коммита транзакции — гейтвей не раздать
  докоммитное состояние.
- Keepalive: протокольные ping-кадры каждые 25 c (как heartbeat SSE);
  не ответивший pong — `terminate()`. `@Public()` на классе гейтвея
  обязателен: JwtAuthGuard читает рефлектор и в WS-контексте.
- Фронт: `startSeatStream/stopSeatStream` в movies-сторе, модалка стартует
  поток на открытии и смене сеанса, глушит на закрытии. Браузерный
  WebSocket не переподключается сам (в отличие от EventSource) — ручной
  backoff `min(1 c · 2ⁿ, 15 c)` + jitter, по onopen — полный resync
  `loadSeats`, как у SSE-сторов. Страж эпох `seatEpoch`: объект сокета
  в state Pinia оборачивается reactive-прокси и идентичность теряется —
  примитив-счётчик надёжен.
- Место, занятое «при вас», выпадает из выбора с подсказкой «Место X
  только что заняли» — тон тот же, что у 409-ветки сабмита; первый снапшот
  сеанса равен `loadSeats`, подсказка на открытии не вспыхивает.
- Транспорт по пути: nginx — отдельный `location /api/seats` с жёстким
  Upgrade-заголовком (`map $http_upgrade` невозможен: конфиг монтируется
  как server-block в conf.d), vite-прокси `/api` получил `ws: true`.
- Демо на Pages: живая карта без сети. Пока модалка открыта, движок каждые
  7–15 c приводит «другого зрителя»: занимает свободное место (никогда —
  из вашего выбора, `avoid`-список) или освобождает своё — только из
  собственной карты `viewerSeats`, сиды и аншлаг-сеанс «КиноКлуба»
  неприкосновенны; ветвь освобождения зовёт `releaseWaitlist` — паритет
  с точками API.

### Бонусная программа

Кэшбэк с подтверждённых броней и оплата бонусами — курс 1 бонус = 1 ₽.
Счёт устроен **ledger'ом, как деньги**: таблица `bonus_transactions` —
только вставки (kind `accrual`/`spend` + причина), баланс нигде не
хранится, а считается от источника `SUM(accrual) − SUM(spend)` по
`user_id`. Снимок `bookings.bonus_spent` (зеркало `discount_rub`
промокодов) показывает, сколько бонусов вчёно в оплату.

- **Начисление** — вердиктом воркера: `handleProcessed` пишет
  `accrual/cashback` = `floor(total_rub × BONUS_CASHBACK_PERCENT / 100)`
  (env, дефолт 5) **той же транзакцией** со статусом CONFIRMED — кэшбэк
  не может начислиться без переключения статуса. Гостевые брони без
  владельца не зарабатывают; нулевой кэшбэк (копеечная оплата после
  скидок) строки не пишет.
- **Списание** — в `pay()` рядом с промокодом: `useBonuses` ≤ половины
  суммы после промо (`floor(base × 0.5)`) и ≤ баланса. Отказы — 409
  `bonusOverLimit` / `bonusInsufficient` / `bonusUnavailable` (гостевая
  бронь), транзакция откатывается целиком: бронь остаётся payable,
  промо-активация тоже.
- **Ledger как деньги — гонки**: после вставки spend-строки контрольный
  пересчёт `SUM` не должен уйти в минус — две параллельные оплаты одним
  балансом разрешает эта проверка, проигравший откатывается. Идемпотентность
  ределивери — `uq(booking_id, reason)`: одна операция одного типа по
  бронь, дубль упирается в констрейнт (`orIgnore` у insert-QB).
- **Реверсы**: FAILED возвращает списанное (`accrual/payment_failed`);
  возврат CONFIRMED-брони (CANCELLED по саге) возвращает списанное
  (`accrual/refund`) и гасит кэшбэк (`spend/clawback`) — но не в минус:
  потраченный кэшбэк гасим сколько есть; REFUND_FAILED (бронь остаётся
  в CONFIRMED) бонусы не трогает. Всё — одной транзакцией с вердиктом.
- **Счёт**: `GET /api/bonuses/my` — баланс от источника + история
  движений свежими сверху (`limit` 1..100). Арифметика — чистые функции
  `bonus.logic.ts` (процент/лимит), на вебе их зеркало `shared/lib/bonus`
  (паттерн промокодов): превью и демо считают как бэк.
- **UI**: блок «Списать бонусы» на `/pay` — чекбокс подставляет максимум
  `min(половина чека, баланс)`, ручной ввод зажимается, промокод сужает
  потолок; 409 между превью и оплатой — подсказка и свежий счёт, бронь
  остаётся оплачиваемой. В `/my` — карточка счёта с историей и
  человекочитаемыми причинами; SSE-вердикты брони подтягивают баланс сами.
- Демо на Pages: ledger в миниатюре — сид счёта 350 бонусов с историей,
  списание/кэшбэк/реверсы считает движок зеркалом API, uq-дубль не
  вставляется.

### Админ-аналитика

`GET /api/admin/stats` — дашборд владельца кинотеатра. Только роль admin
(401 без JWT, 403 обычному пользователю); в демо-режиме на Pages дашборд
открыт всем — это витрина. Агрегаты считаются чистыми функциями по
выгрузке строк (`apps/api/src/admin/admin-stats.logic.ts`, паттерн
`booking.logic.ts`): объём демо-кинотеатра мал, зато zero-fill дней, топы
и KPI честно покрываются юнит-тестами; при росте — `GROUP BY` в SQL без
смены контракта.

- Сводка KPI: выручка (`SUM total_rub` по CONFIRMED), средний чек,
  проданные места, средняя заполняемость предстоящих сеансов, фильмы,
  отзывы и средняя оценка сети.
- Счётчики по всем 7 статусам статусной машины, нули включительно.
- Топ-5 фильмов по подтверждённым броням (ничья — по выручке).
- Ближайшие 8 сеансов с заполняемостью: занятость — `seat_occupancy`
  (включая неоплаченные резервы), вместимость зала — 80.
- График выручки за 14 дней: день вердикта воркера (`processed_at`,
  фолбэк — день создания), локальные дни, пустые — нулевые столбцы.
- Кэш: `admin:stats:v1` в Redis, TTL 30 c, конверт `{source, data}` как
  у каталога — перекликивание дашборда не молотит Postgres.
- Экран `/admin/stats`: 9 плиток сводки + 7 статусов, SVG-график выручки
  без библиотек (цвета — токены темы), полосы заполняемости
  зелёная → жёлтая (50%) → красная (80%). В демо данные дают сид-брони
  «других зрителей» за две недели; кэш 30 c зеркалит Redis, а CONFIRMED-сиды
  держат места в картах сеансов, но прав на отзыв не дают.

### Документация API (Swagger)

Живая OpenAPI-документация — [Swagger UI](http://localhost:13000/api/docs)
на стенде (и через nginx: `:18080/api/docs`), спека — `/api/docs-json`:

- Каркас — `apps/api/src/swagger.ts` (`setupSwagger`, вызывается из
  `main.ts`): заголовок, версия, `addBearerAuth()`. UI регистрируется
  в обход Nest-роутера, поэтому глобальный `JwtAuthGuard` его не трогает —
  документация открыта, как витрина (это фиксируется тестом).
- Схемы запросов описаны `@ApiProperty` в DTO; ответные DTO — классы
  (не интерфейсы) при сущностях: `MovieDto`, `BookingDto`, `ReviewDto`,
  `SeatMapDto`, `UserDto`, `LoginResult`. Union-типы (роли, статусы
  lifecycle) и nullable-поля перечислены явно — `reflect-metadata` их
  не различает.
- Контроллеры размечены тегами по доменам, саммари и кодами ответов:
  409 `seatsTaken`/`reviewExists`/гонки статусов, 403 без прав,
  SSE-стрим с пояснением, почему он публичен.
- Try-it-out: нажмите **Authorize** и вставьте `accessToken` из
  `POST /api/auth/login` — мутации заработают прямо из браузера.
  Спека при этом не врёт о безопасности: защищённые маршруты помечены
  `security: bearer`, витрина — нет (проверяется интеграционным тестом).

### Фронт: Feature-Sliced Design

`apps/web/src` разбит по методологии [FSD](https://feature-sliced.design/ru/) —
слои строго сверху вниз, импортировать можно только из нижележащих,
внутри слоя — только из своего среза. Границы проверяет ESLint
(`eslint-plugin-boundaries`), нарушение валит CI:

```
app/        корень: main.ts, App.vue, роутер, глобальные стили
pages/      экраны: home, bookings, my-bookings, payment, ticket, login,
            forgot-password, reset-password, profile, admin, admin-stats
widgets/    крупные композиционные блоки: app-header
features/   сценарии пользователя: booking-flow (модалка + схема зала), review
entities/   бизнес-сущности: movie (+отзывы и расписание), booking, viewer,
            stats, promo, ticket, waitlist, bonus
shared/     без бизнес-логики: api-клиент и контракты, демо-движок, lib, config,
            ui (QrCode — SVG-рендер QR)
```

### Демо-режим на GitHub Pages

Pages раздаёт только статику, поэтому опубликованная сборка при
недоступном API прозрачно переключается на локальную симуляцию:
те же события, тайминги и вероятности, что у Go-воркера, включая
lifecycle оплаты — окно резерва с экспирацией, pay-вердикты, саги —
и аккаунт: вход/регистрация/профиль/смена пароля/восстановление
с теми же кодами ошибок, что у API. Промокоды тоже честные: на экране
оплаты работают `CINE10` (−10%) и `SUMMER300` (фикс −300 ₽, почти
исчерпан), `EXPIRED5` показывает 410; промо-секция админки `/admin`
открыта в демо всем — код можно создать свой. QR-билеты живут полной
жизнью: после CONFIRMED-вердикта «воркера» у брони появляются билеты
(ссылка с экрана оплаты и с демо-табло), отмена гасит их; сканер
движка отвечает теми же вердиктами, что API. Лист ожидания тоже
честный: сеанс «КиноКлуб» — сид-аншлаг, вход в очередь с позицией,
освобождение места «уведомляет» голову, а бронь уведомлённого гасит
запись — те же WAITING → NOTIFIED, что у API. Живая карта — без
WebSocket, но с «другими зрителями»: пока модалка выбора открыта,
движок каждые 7–15 c занимает или освобождает чужое место — карта
шевелится, выбранное вами не уводят. Бонусный счёт стартует с 350
бонусов и живёт ledger'ом движка: кэшбэк 5% капает с CONFIRMED-вердиктов,
на `/pay` можно списать до половины чека (кулак правил как у API —
`bonusOverLimit`/`bonusInsufficient` честные), отмена брони разворачивает
начисления.
Интерфейс — продуктовый, без служебных пометок о стеке и режиме:
вся архитектура и схема запуска описаны в этом README. Витрина —
скелетоны загрузки, жанр-фильтры, карта зала с баром занятости,
экран оплаты, тёмная/светлая тема (тумблер в шапке, без мигания при
загрузке) и мобильная доводка (скролл тела модалки, листаемая
навигация). Дашборд `/admin/stats` в демо открыт всем: плитки, топ
фильмов и график выручки считаются из сид-броней «других зрителей».
Собранная страница живёт
в `CineBooking/` в корне репозитория; пересборка:

```bash
cd apps/web && npm run build
# демка — в CineBooking/ в КОРНЕ репозитория портфолио (не в fullstackProject!)
```

## Переменные окружения

См. [.env.example](.env.example). В docker compose всё уже настроено.
Дефолт `DATABASE_URL` API в коде — `postgres://cine:cine@localhost:15432/cine`
(порт compose-стенда). У notification-service своя пара: `STORAGE=memory|postgres`
(дефолт `memory` — стенд без БД не падает) и собственный `DATABASE_URL`
на базу `cine_notifications`. Секреты: `JWT_SECRET` (подпись токенов)
и `TICKETS_SECRET` (HMAC-подпись QR-билетов; смена гасит все выданные
билеты) — dev-дефолты только для стенда.

`PAYMENT_TIMEOUT_MS` (только API) — окно оплаты брони: TTL wait-очереди
RabbitMQ и дедлайн `expires_at`. Дефолт в коде — 15 минут, compose-стенд
держит 2 минуты, чтобы экспирацию было видно руками и в e2e. Поменяли
значение на живом брокере — пересоздайте очередь (`docker compose down`,
у rabbitmq нет volume, но аргументы живут между рестартами контейнера).
e2e берёт окно из `E2E_PAYMENT_TIMEOUT_MS` (дефолт 120 000 = стенд).

`RESET_LINK_BASE` (только API) — база одноразовой ссылки сброса пароля в
«письме»: дефолт `http://localhost:18080/#/reset-password` (фронт стенда).
Историю уведомлений для e2e-сброса задаёт `E2E_NOTIF_URL`
(дефолт `http://localhost:18082`).

## Заметки

- Схема БД управляется SQL-миграциями TypeORM (`apps/api/src/migrations`);
  `synchronize` удалён. Старые docker-томы, где схему собрал `synchronize`,
  нужно один раз сбросить: `docker compose down -v && docker compose up --build`
  (миграции пересоздадут схему, фильмы послеются заново).
- Обмен `cinema` и retry-топологию (`*.retry`, `*.parking`) объявляют и API,
  и воркер одинаковыми параметрами — кто стартует первым, тот и создаёт.
  Стек с уже созданными очередями без этих аргументов нужно пересоздать
  (`docker compose down -v`): у `<очередь>.retry` теперь есть аргументы TTL/DLX,
  и повторная декларация со старыми параметрами не пройдёт.
- SSE через nginx требует `proxy_buffering off` (уже в `apps/web/nginx.conf`),
  иначе события осядут в буфере прокси и не дойдут до EventSource.
