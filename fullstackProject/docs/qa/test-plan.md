## 1. Цель и задачи

Цель — подтвердить, что система бронирования корректно выполняет свои функции
на всех уровнях: от чистой логики до сквозного потока через брокер сообщений,
и что деградация любого компонента обрабатывается предсказуемо.

Задачи:

- определить объём и границы тестирования;
- выбрать виды и уровни тестирования под каждый риск;
- зафиксировать критерии начала/окончания, приостановки/возобновления;
- описать окружения, инструменты и метрики;
- обеспечить трассируемость «требование → тест-кейс».

## 2. Объект тестирования

| Компонент | Стек | Что делает |
|---|---|---|
| `apps/api` | NestJS 11, TypeORM, ioredis, @golevelup/nestjs-rabbitmq | REST + SSE, транзакции, кэш, события |
| `apps/web` | Vue 3, Vite, Pinia | SPA: каталог, карта зала, брони, демо-режим |
| `services/ticket-worker` | Go, amqp091 | «платёжный шлюз»: оплата и возвраты |
| Инфраструктура | PostgreSQL 16, Redis 7, RabbitMQ 3.13, nginx | docker compose стенд |

Ключевые бизнес-потоки:

1. **Бронирование**: выбор мест → `POST /api/bookings` → `PENDING` → воркер
   «платит» (1,2–2,8 c, ~90% успеха) → `CONFIRMED`/`FAILED`; при `FAILED`
   места освобождаются.
2. **Отмена (компенсирующая сага)**: `CONFIRMED → CANCELLING → CANCELLED`
   (возврат 0,8–1,6 c, ~90% успеха) либо откат в `CONFIRMED` при отказе банка.
3. **Живые обновления**: SSE `/api/bookings/stream` — событие `booking` на
   каждую мутацию, heartbeat `ping` каждые 25 c, resync по переподключению.

## 3. Границы тестирования

**Входит:**
- функциональность API, воркера, SPA (включая демо-режим);
- согласованность контрактов событий RabbitMQ между NestJS и Go;
- конкурентный доступ к местам (гонки, двойные клики);
- отказоустойчивость: недоступность Postgres/Redis/RabbitMQ, обрыв SSE;
- корректность кэша и его инвалидация по TTL.

**Не входит (осознанные ограничения пет-проекта):**
- нагрузочное тестирование (нет SLA по RPS);
- безопасность, отличная от базовой (нет аутентификации — она не заявлена);
- кросс-браузерная матрица (Chrome/Edge актуальных версий);
- UI-автотесты (Playwright и т.п.) — покрытие даёт интеграционный/e2e-уровень.

## 4. Виды и уровни тестирования

Пирамида: основная масса — быстрые детерминированные тесты логики, вершина —
немного «живых» сквозных проверок.

| Уровень | Инструмент | Что проверяет | Кол-во | Время прогона |
|---|---|---|---|---|
| Юнит (API) | jest + fakes | логика брони, места, сага, SSE-шина, кэш, health | 43 | ~10 c |
| Юнит (web) | vitest + fake timers | форматтеры, зал, демо-движок, сторы (вкл. EventSource-двойник) | 43 | ~2 c |
| Интеграционный | jest + supertest + fetch | HTTP-стек Nest целиком на фейковых БД/брокере/Redis, включая SSE по живому сокету | 25 | ~9 c |
| E2E | jest + fetch против docker-стенда | весь контур с Go-воркером и RabbitMQ; пропускается, если стенд не поднят | 8 | ~20 c |
| Ручное | чек-листы | UX, визуальное, RabbitMQ UI, nginx-специфика | — | по требованию |

Функциональные виды: позитивные, негативные, граничные значения, конкурентные
сценарии. Нефункциональные: надёжность (реконнекты воркера и SSE), усечение
производительности не тестируем (см. границы).

## 5. Критерии

**Входа в тестирование:**
- `npm install` проходит во всех пакетах, `go build` — без ошибок;
- юнит- и интеграционные наборы зелёные на текущей ветке.

**Выхода (готовность релиза):**
- все наборы зелёные: `npm test` (api, web), `test:integration`;
- e2e зелёный на стенде `docker compose up --build`;
- нет открытых дефектов Sev.1/Sev.2; Sev.3/Sev.4 — с согласованием;
- матрица трассировки не содержит непокрытых требований уровня High.

**Приостановки:** стенд не поднимается, более 30% кейсов блокированы
инфраструктурным дефектом. **Возобновления:** блокер исправлен и перепроверен.

## 6. Риски и их снижение

| Риск | Вероятность | Влияние | Смягчение |
|---|---|---|---|
| Гонка за одно место из двух вкладок | Средняя | Высокое | уникальный констрейнт `(movie_id, seat)` + интеграционный тест 409 |
| Двойной клик «Отменить» | Средняя | Среднее | условный `UPDATE … WHERE status='CONFIRMED'` + тесты 409 |
| Недоставленное событие RabbitMQ | Низкая | Высокое | durable-очереди, ack после публикации, идемпотентный consumer |
| «Залипание» SSE за прокси | Средняя | Среднее | `proxy_buffering off`, heartbeat, resync по onopen |
| Ределивери `booking.refunded` | Низкая | Среднее | пропуск события вне `CANCELLING` + тест на ределивери |
| Вероятностные вердикты воркера (~10% отказ) | — | Низкое | в тестах вероятность фиксируется моком/переменными окружения |

## 7. Окружения

| Окружение | Как получить | Примечание |
|---|---|---|
| Локальный полный (docker) | `docker compose up --build` | web :18080, api :13000, RabbitMQ UI :15672 (guest/guest), worker :8081, pg :15432 |
| Локальный гибрид | `docker compose up -d postgres redis rabbitmq` + `npm run start:dev` | быстрая итерация по коду |
| CI/юнит | без инфраструктуры | e2e корректно пропускается |
| Демо (GitHub Pages) | https://dimas1barabas.github.io/CineBooking/ | без бэкенда: локальная симуляция |

Переменные для детерминизма: `SUCCESS_RATE`, `REFUND_SUCCESS_RATE`,
`PROCESS_MIN_MS/MAX_MS`, `REFUND_MIN_MS/MAX_MS`, `E2E_BASE_URL`.

## 8. Метрики и отчётность

- прохождение по наборам (passed/failed/skipped) — фиксируется в отчёте прогона;
- покрытие кода тестами: `cd apps/api && npm run test:cov`;
- число дефектов по severity, найдено/исправлено за итерацию.

Шаблон отчёта о прогоне — в [test-cases.md](test-cases.md#отчёт-о-прогоне-шаблон).

## 9. Порядок работ (итерация)

1. Регресс базовых наборов (юнит + интеграция) — на каждый PR.
2. Прогон e2e на стенде — перед слиянием в `main`.
3. Ручная проходка чек-листов по изменённой области.
4. Обновление матрицы трассировки при добавлении требований.

## 10. Роли

В пет-проекте роли совмещены: разработчик = автор тестов = исполнитель
ручных проверок; ревьюер — второй участник рецензирует тест-кейсы и отчёты.
